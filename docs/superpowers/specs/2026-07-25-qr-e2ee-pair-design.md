# QR pairing carries E2EE account_key (wrap-only)

**Date**: 2026-07-25
**Branch**: v0.3-dev
**Status**: design

## Problem

The mobile QR pairing path (`/api/pair/consume`) mints a valid session token
but **never conveys the OPAQUE-derived `account_key`** to the mobile client.
After v0.3's M6-final work stripped plaintext `title` / `cwd` / `command` /
`current_command` from `SessionInfo` on the relay (`e312b7e`, `cff1e71`),
those fields ship only as AEAD-sealed `sealed` envelopes decryptable with the
session owner's `account_key`. A mobile paired via QR has no `account_key`, so
the list falls back to `session_id.slice(0, 8)` — an 8-char hex — and the
detail lines (title, cwd) are blank.

The `account_key` is deterministically derived from the user's password
through OPAQUE and is never present on the server in plaintext, so the relay
cannot simply return it in the consume response. Requiring the user to type
their password on the phone after every scan defeats the entire "scan once,
done" UX QR pairing exists to provide.

## Goals

1. After a mobile scans a QR generated by a desktop whose `account_key` is
   currently unlocked, the mobile can decrypt sealed session fields for that
   owner — no password prompt on the phone.
2. The relay MUST NOT observe `account_key` in plaintext at any point. This
   preserves the invariant every M1–M6-final commit was written to uphold.
3. Aligns the QR consume path with OPAQUE login by returning `realm_id` and
   `home_instance_url` (currently omitted, a latent bug independent of this
   spec's core concern).

## Non-goals

- Web-as-QR-generator support. Only the desktop app displays pairing QRs
  today (`PairingPanel.vue` calls the Wails-bound `CreatePairingToken`); the
  web bundle has no equivalent surface.
- Web-as-QR-consumer support. Only the mobile Capacitor app scans QRs.
- Changing how `account_key` is derived, cached on desktop, or anchored to
  `realm_id`. Those are stable (`7ecf9ad`).
- Any change to the OPAQUE login path.
- Rotating `account_key`. If a QR (with `k=`) leaks, the security posture
  matches Signal Desktop / WhatsApp Web QR pairing: the leaked key window is
  bounded by the 5-minute pair-token TTL, the single-use consume race, and
  the physical fact that the QR was on-screen briefly.

## Architecture

```
┌─────────────┐    ① POST /api/pair/create ┌──────────┐
│  Desktop    │    { wrap: AEAD(ak, wk) }  │  Relay   │
│  ak unlocked│  ────────────────────────► │  stores  │
│             │                            │  wrap in │
│  ② random wk│  ◄──────────────────────── │  pairing │
│  ③ QR       │    { token, expires_at }   │  _tokens │
│    ?t=…&k=…│                            └──────────┘
└─────────────┘                                  ▲
       │                                         │
       │ (scan)                                  │ ⑤ POST /api/pair/consume
       ▼                                         │    { token }
┌─────────────┐                                  │
│  Mobile     │  ◄───────────────────────────────┘
│  ④ wk ← QR  │  { session_token, wrap, realm_id, ... }
│  ⑥ ak = AEAD⁻¹(wrap, wk)
│  ⑦ Keychain │
└─────────────┘
```

**Invariant**: `account_key` plaintext exists only in desktop memory and, after
step ⑦, in the mobile Keychain. The relay sees only `wrap` (ciphertext) and
never `wk`.

## Threat model

| Adversary | Reveals | Result |
|---|---|---|
| Relay operator / DB dump | `wrap`, `pair_token_hash` | ✗ No `wk`. XChaCha20-Poly1305 requires the key. |
| Passive network observer (TLS intact) | Nothing | ✗ |
| Passive network observer (TLS broken) | `wrap`, `session_token`, `pair_token` (plaintext) | ✗ `wk` never crosses the network. |
| Shoulder-surfer / QR photo mid-pairing | `pair_token`, `wk` | ✓ IF they race the legit mobile to consume within TTL (5 min). Winning yields `ak`. Losing yields nothing useful — the consumed `pair_token` is dead. |
| QR photo AFTER pairing completes | `wk` only | ✗ `wrap` is bound to the consumed row; even if not garbage-collected, the pair_token is dead so nobody can re-consume to retrieve it. |
| Leaked `wk` alone (no relay access) | `wk` only | ✗ No ciphertext to decrypt. |

Equivalent to Signal Desktop / WhatsApp Web pair-QR threat model.

## Wire schema

### QR URL

```
<relay_https_url>/pair?t=<pair_token>&k=<wrap_key_b64url_nopad>
```

- `t=<pair_token>` — unchanged (`pair_` + 43 base64url chars = 47 chars).
- `k=<wrap_key>` — 32 random bytes encoded as base64url no-pad (43 chars).
- Total added: `&k=` + 43 = 46 chars. Existing QRs are ~100 chars → ~146 chars
  post-change. QR version ~10 (well within camera capability).

`k=` is absent iff the desktop generated the QR while `account_key` was
locked (see "Desktop generates locked QR" below).

### Wrap blob (Go → DB → mobile)

Byte layout mirrors the existing `SealedSessionFields` envelope so we reuse
its known-good primitives:

```
byte 0        : cipher_id, 0x01 = XChaCha20-Poly1305
bytes 1..24   : nonce (24B, random per wrap)
bytes 25..    : ciphertext || tag (32B account_key + 16B Poly1305 tag)
── total 73 bytes ──
```

Base64 (std) encoded on the wire between desktop→relay and relay→mobile
(~100 chars). Column type on DB is `BLOB` / `BYTEA` — raw bytes, no b64.

### AEAD parameters

- **Cipher**: XChaCha20-Poly1305 (matches existing `SealedSessionFields`
  layer).
- **Key**: `wk` (32 random bytes, generated once per QR, never persisted on
  desktop or relay).
- **Nonce**: 24 random bytes per wrap, embedded in the blob (byte 1..24).
- **Plaintext**: raw `account_key` bytes (32B; no JSON wrapper — length is
  fixed so the framing is unambiguous).
- **AAD**: constant ASCII string `"atterm-pair-wrap-v1"` (19 bytes).

**Why AAD is only a version tag**: an earlier draft bound AAD to
`pair_token_hash`, but desktop generates `wk` and the wrap ciphertext BEFORE
`pair_token` is minted (relay mints it in response to the create request that
carries the wrap). Sequencing the wrap after token creation would require a
second round-trip. A version-tag AAD prevents cross-scheme replay if we ever
introduce a `-v2` envelope, and adds no security beyond that. The security
of a single wrap rests on `wk` being unique and unknown.

## Relay changes

### Migration `0011_pairing_wrap.sql`

Both `internal/userstore/migrations/sqlite/0011_pairing_wrap.sql` and
`internal/userstore/migrations/postgres/0011_pairing_wrap.sql`:

```sql
-- sqlite
ALTER TABLE pairing_tokens ADD COLUMN wrapped_account_key BLOB;

-- postgres
ALTER TABLE pairing_tokens ADD COLUMN wrapped_account_key BYTEA;
```

Nullable + additive; downgrade-safe.

### Store `internal/userstore/pairing.go`

Extend the signatures — no new methods, just parameters:

```go
func (s *SQLiteStore) CreatePairingToken(
    ctx context.Context,
    userID string,
    ttl time.Duration,
    wrap []byte,      // NEW: may be nil
) (Secret, *PairingToken, error)

func (s *SQLiteStore) ConsumePairingToken(
    ctx context.Context,
    plaintext string,
) (*User, []byte /* NEW: wrap, nil if none */, error)
```

`ConsumePairingToken` reads `wrapped_account_key` in the same SELECT that
loads `user_id/expires_at/consumed_at`. No separate query. The wrap is
returned regardless of whether it's nil.

Row is NOT deleted post-consume (matches today: `consumed_at` is stamped,
row retained for audit). The wrap stays in the row too — the `consumed_at IS
NULL` guard in the atomic UPDATE ensures nobody can re-consume, so leaving
wrap in place doesn't broaden exposure.

### `POST /api/pair/create`

Request body extended:
```json
{ "wrap": "<b64std>" }   // optional; empty/absent → NULL
```

Response unchanged: `{token, expires_at, qr_url}`.

Note: `qr_url` server-side still emits `…/pair?t=<token>`. The `&k=<wk>`
suffix is appended by the **desktop** wrapper (`app.go`
`CreatePairingToken`), NOT by the relay — the relay never sees `wk` and
cannot construct it.

### `POST /api/pair/consume`

Response body extended:
```json
{
  "session_token": "...",
  "expires_at": ...,
  "user": {"id": "...", "email": "..."},
  "realm_id": "...",              // NEW — parity with OPAQUE login
  "home_instance_url": "...",     // NEW — parity with OPAQUE login
  "wrap": "<b64std>"              // NEW — omitted iff row's column is NULL
}
```

Realm ID and home instance URL come from the same lookup path the OPAQUE
login uses (`a3a54f9`). If the store returns them empty, the fields are
omitted from JSON (`omitempty`) so old mobiles don't see keys they don't
understand.

## Desktop changes

### New file: `desktop/wrap_account_key.go`

Pure crypto helper — one function, testable without app state:

```go
package main

// wrapAccountKey seals ak into a 73-byte envelope under a freshly-generated
// 32-byte wrap_key. Returns (envelope, wrapKey, error). Envelope layout:
// cipher_id(1) || nonce(24) || AEAD_seal(ak, wk, nonce, AAD).
// AAD is the constant string "atterm-pair-wrap-v1".
func wrapAccountKey(ak []byte) (envelope, wrapKey []byte, err error)
```

Uses `golang.org/x/crypto/chacha20poly1305`'s XChaCha20-Poly1305 constructor,
consistent with the `internal/e2eeclient` and desktop uplink sealing paths.

### `desktop/app.go` `CreatePairingToken`

```go
func (a *App) CreatePairingToken() (PairingTokenResponse, error) {
    // ... existing config load / validation ...

    ak := a.accountKeySnapshot()
    var wrapB64 string
    var wk []byte
    if len(ak) > 0 {
        env, w, err := wrapAccountKey(ak)
        if err != nil {
            log.Printf("desktop: wrap account_key for pair: %v", err)
        } else {
            wrapB64 = base64.StdEncoding.EncodeToString(env)
            wk = w
        }
    }

    reqBody := map[string]string{}
    if wrapB64 != "" { reqBody["wrap"] = wrapB64 }
    body, _ := json.Marshal(reqBody)

    // POST /api/pair/create with body; parse response as before.
    // ...
    out.QRURL = out.QRURL   // relay's value
    if len(wk) > 0 {
        sep := "&"
        if !strings.Contains(out.QRURL, "?") { sep = "?" }
        out.QRURL = out.QRURL + sep + "k=" + base64.RawURLEncoding.EncodeToString(wk)
    }
    return out, nil
}
```

Also extend `PairingTokenResponse` with `Wrapped bool` (set true iff the
final QR URL carries `k=`, i.e. `ak` was unlocked AND wrap succeeded) so
the frontend can render the "will decrypt on mobile" affordance.

**Failure mode**: if `wrapAccountKey` returns an error (e.g. rand read fails)
we log and continue with `wrapB64=""`, `wk=nil`, `Wrapped=false`. Never
propagate — a connectivity-only QR is strictly better than a broken pair
flow. This keeps the "locked → no wrap" and "unlocked but crypto error →
no wrap" cases indistinguishable to the UI (both render the "no E2EE"
banner), which is desirable — the user's remediation is the same.

### `PairingPanel.vue`

## Mobile changes

### New export in `desktop/frontend/src/lib/opaque.ts` (and web mirror)

```ts
const PAIR_WRAP_AAD = utf8ToBytes('atterm-pair-wrap-v1')

/** openAccountKeyWrap AEAD-opens a wrap envelope produced by the desktop's
 *  wrapAccountKey. Returns the raw 32-byte account_key or null on any
 *  structural / cipher error. */
export function openAccountKeyWrap(
  envelope: Uint8Array | number[] | null | undefined,
  wrapKey: Uint8Array,
): Uint8Array | null
```

Same structural checks as `openOutFrame` (min length, cipher_id byte,
XChaCha20-Poly1305 decrypt with the constant AAD). Mirror to
`web/src/shared/lib/opaque.ts` (per the existing mirror rule at
`desktop/frontend/src/lib/opaque.ts:103`).

### `desktop/frontend/src/mobile/PairingConsume.vue`

`parseScanned` now returns `{ origin, token, wrapKey?: Uint8Array }`:

```ts
function parseScanned(raw, allowInsecure): { origin, token, wrapKey?: Uint8Array } | string {
  // ... existing URL parse ...
  const token = u.searchParams.get('t')
  if (!token || !u.host) return 'pair_invalid_url'
  const k = u.searchParams.get('k')
  let wrapKey: Uint8Array | undefined
  if (k) {
    try { wrapKey = b64UrlNoPadToBytes(k) } catch { return 'pair_invalid_url' }
    if (wrapKey.length !== 32) return 'pair_invalid_url'
  }
  return { origin: u.origin, token, wrapKey }
}
```

Then pass `wrapKey` down to `platform.relay.consumePairing(origin, token, wrapKey)`.

## Backward compatibility

Per `feedback_no_backward_compat`: v0.3 is a single-user project on active
migration. We require:
- Relay: this release (has `0011_pairing_wrap.sql` + new consume response fields).
- Mobile app: this release (parses `k=`, calls `openAccountKeyWrap`).
- Desktop app: this release (generates wrap + `k=` suffix).

Cross-version behaviour is nevertheless graceful:
- Old QR (no `k=`) on new mobile → `wrapKey` undefined → decrypt skipped →
  behaves as today (session works, sealed fields render blank).
- New QR (`k=…`) on old mobile → mobile ignores unknown query param → today's
  behaviour.
- Old mobile hitting new relay → new relay adds `wrap` field to response →
  old mobile ignores unknown JSON key.
- New mobile hitting old relay → response lacks `wrap` → decrypt skipped →
  today's behaviour.

Migration is column-add-nullable; a downgrade leaves an unread column,
harmless.
