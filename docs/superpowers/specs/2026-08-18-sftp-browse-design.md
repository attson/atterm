# SFTP 浏览与传输（P6 第 28 项）— design

Date: 2026-08-18
Status: Drafted — awaiting user review before plan.
Parent: [2026-08-16 sync-layer roadmap](./2026-08-16-sync-layer-roadmap-design.md) §5 P6 第 28 项 · roadmap 第 28 项

## 0. Summary

给 fileExplorer 加第三个数据源：SSH 主机。只读目录浏览 + 单文件上传（下载到本机磁盘是 Non-Goal，见 §3）。

母 spec 把本项的第一个问题定为「验证 `FS_REQUEST` 通道在 SSH 往返延迟与大目录下的表现，不适配则退回独立通道」。**这个问题问错了地方，答案也不是退回独立通道。**

查下来：帧类型没问题，relay 的路由表也没问题。问题在桌面端**把 FS 操作同步执行在 uplink 的读循环里**——而那条读循环同时在处理击键。见 §1。

## 1. 真正的阻塞点

`desktop/uplink.go:398-471` 是一个 `switch`，同一个读循环里处理：

| 帧 | 含义 |
|---|---|
| `TypeIn` | **用户击键** |
| `TypeResize` | 窗口尺寸 |
| `TypePasteImage` | 粘贴 |
| `TypeFSRequest` | 文件操作 |
| `TypeClaimDriver` / `TypeViewers` / … | 控制帧 |

而 `TypeFSRequest` 这一支走到 `desktop/remote_fs.go:337` 的 `fs.handle(sessionID, req)`——**同步调用，没有 goroutine，没有超时**。

本地文件系统上这没问题，一次 `listDir` 是微秒级。但 SFTP 一次目录列举要一个甚至多个 SSH 往返；经第 27 项的跳板链更是逐跳累加。

**后果：一次慢的 SFTP 列目录会卡住这条 uplink 上所有会话的击键。** 用户的体感是「终端卡死了」，而他做的只是点开一个远程目录。

所以本项的第一件事不是选通道，是**把 FS 执行挪出读循环**。

### 1.1 relay 侧的次要问题

`internal/relay/fs_router.go` 是纯路由表：按 `requestID` 注册一个出口 channel，响应回来时转发。**没有 TTL，没有超时**（全文件 grep `timeout`/`context` 零命中）。

一个永远收不到响应的请求会一直占着注册项，直到客户端断开时 `unregisterClient` 兜底。本地 FS 下这几乎不可能发生；SFTP 下「远端卡住不回」是常态之一。这不是崩溃，是缓慢的资源堆积，但既然要接 SFTP 就该一并处理。

## 2. Goals

- fileExplorer 能以 SSH 主机为数据源，只读浏览目录。
- 单文件上传（本机 → 远端）。
- **一次慢的远程 FS 操作不影响任何会话的击键。**

## 3. Non-Goals

- **不做单文件下载（远端 → 本机）到磁盘。** 这一条原本写在 Goals 里，现在挪到这里：落盘需要一个保存对话框和一套目标目录选择，那是一个新的用户界面，不属于「接上第三个数据源」。读远端文件仍然做，但只喂给预览和编辑器，不在本机另存一份；SSH host 上的图片 / PDF 因此看不了内容。**是推迟，不是取消**——单独记在 roadmap 第 33 项。
- 不做递归下载 / 目录同步。
- 不做远端文件编辑（现有的 remote 编辑走的是另一条路径，本项不动）。
- 不做断点续传。
- 不做 SFTP 之外的传输方式（不做 scp 回退）。

## 4. 机制

### 4.1 执行挪出读循环

`handleRemoteFSRequest` 改为把请求投递给一个**每会话的有界工作池**，读循环立刻返回继续收帧。

有界是关键：无界 goroutine 意味着一台卡住的远程主机可以让请求无限堆积。池满时对新请求**立即返回一个明确的「忙」错误**，而不是排队等待——排队会把延迟藏起来，直到用户以为点击没反应。

这一步**独立于 SFTP**，它同时修好了本地 FS 在慢磁盘（网络挂载、休眠的外置盘）下的同一问题。因此它自成一个任务，有自己的回归测试：**断言一个慢 FS 操作进行中，同一 uplink 上的 `TypeIn` 仍然被处理**。

### 4.2 SFTP 执行器

新增 `internal/sftpfs`（或 `desktop/sftp_source.go`，视依赖方向定），实现与 `fsaccess` 相同的操作集：`listDir` / `fileMeta` / `readChunk`，加上写路径。

底层用 `github.com/pkg/sftp` 架在第 27 项的 `sshclient.Conn` 上——**这意味着 SFTP 天然继承跳板链**：`Conn` 已经可能是一条链的终点，`sftp.NewClient` 不关心它怎么来的。

连接复用第 26 项的 per-host 引用计数（`hostConn`）：一台主机的 SFTP 会话与它的隧道共用同一条 SSH 连接，引用归零时一起关。**不为 SFTP 单开一条连接**——那会在远端多出一个登录、多一份 keepalive。

### 4.3 数据源的第三态

fileExplorer 现在有本机与远端 host 两个源。第三个是 SSH host，选择器里按已保存主机列出。

带 `ProxyCommand` 的主机**不出现在列表里**（连不上），带 `ProxyJump` 的正常出现（第 27 项之后能连）。这个判定必须复用 `hostRunsProxyCommand`，不得新增第三个调用点——第 26/27 项两次 review 都专门守着这个不变量。

## 5. 需要决断的地方

### 5.1 上传是覆盖还是拒绝

上传到一个已存在的远端路径时：默认**拒绝并说明**，而不是静默覆盖。

理由：这条路径上没有回收站也没有版本。一次误覆盖在远端服务器上是不可逆的，而「拒绝」的代价只是用户多点一次确认。现有本地写路径 (`fsaccess_write.go`) 有 `ExpectedModTime` 做乐观并发控制，远端应沿用同一模式而不是另造一套。

### 5.2 大目录

不做分页——但**要有上限**。列举超过 N 条（建议 2000）时截断并**明确告诉用户被截断了**，而不是悄悄少给。

理由和第 25 项跳过条目要报原因一致：**用户看到 12 个文件而目录里有 3000 个，却不知道，是最糟的形态**。

### 5.3 权限与只读

浏览走既有的 `remotePermission` 检查（`remote_fs.go:322`，要求 full）。上传额外要求什么，本设计**先不加新维度**——沿用同一道闸门，避免造出第二套权限语义。

### 5.4 不加密两次

`FS_REQUEST` 的路径段已经有 sealed 处理（`proto.DecodeFSRequest`）。SFTP 执行器拿到的是**已解密的明文路径**，与本地 FS 执行器一致——`remote_fs.go` 的注释明说「下游对加密无感知」。**不要在 SFTP 层再加一层**。

## 6. 风险

1. **把执行挪出读循环会改变本地 FS 的时序。** 现在是严格串行；改成池之后同一会话的两个请求可能并发完成。前端若隐含依赖响应顺序，会暴露。计划里要有一条测试固定「同一 requestID 的响应只有一个」，并检查前端是否按 requestID 配对（应该是，但要验）。
2. **`pkg/sftp` 是新依赖。** 需要确认它是否已在 `go.sum` 里（大概率不在），以及它的维护状态。
3. **凭据。** SFTP 复用主机记录的凭据，与第 26/27 项一致；不新增凭据面。
4. **relay 路由表的 TTL** 是本项顺带修的，但它影响所有 FS 请求而不只是 SFTP —— 要单独测。

## 7. 验证

- **读循环不被阻塞**：一个人为拖慢的 FS 操作进行中，同一 uplink 的 `TypeIn` 仍被处理。这是本项最重要的一条测试。
- 工作池满：返回明确的忙错误，不排队、不 panic。
- SFTP 列目录 / 读文件 / 上传各一条端到端。（「下载」在 §3 已挪为 Non-Goal——读远端文件仍然做，只是不落盘。）
- 上传到已存在路径默认被拒。
- 目录截断：超过上限时结果里带截断标记。
- 跳板：经 `ProxyJump` 的主机能列目录（复用第 27 项的链）。
- `ProxyCommand` 主机不出现在数据源列表里。
- relay 路由 TTL：一个永不响应的请求最终被回收。

## 8. 与母 spec 的差异

- 母 spec 让「验证 `FS_REQUEST` 能否扛住 SSH 延迟，不行就退回独立通道」。**结论是两者都不对**：帧与路由都没问题，问题是桌面端在读循环里同步执行（§1）。退回独立通道不会修好这一点，因为阻塞的是执行而不是传输。
- 母 spec 未提读循环与击键共用。这是本项最重要的发现。
- 母 spec 未提大目录要有上限与截断提示（§5.2）、也未提上传冲突语义（§5.1）。
