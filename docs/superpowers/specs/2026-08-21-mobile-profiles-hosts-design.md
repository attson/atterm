# Mobile: profiles and the SSH host list — design

Roadmap item 32 (P7). "移动端展示并使用 profile" and "移动端展示 SSH 主机清单".

## 1. What "使用" can mean, given that mobile cannot fork a shell

`desktop/frontend/src/platform/capacitor.ts` says, and means:

```
// newSession omitted — capacitor cannot fork local PTYs
```

There is no session-creation path on mobile at all. So "展示" is
straightforward and "使用" is not a UI question: a profile is a recipe for
forking a PTY, and only a desktop forks PTYs. The phone can only *ask* one to.

This design takes that reading. Mobile asks a chosen desktop to open a session
with a chosen profile, then attaches to it through the existing attach path.
The alternative — deliver display only and record that "使用" was dropped —
would be honest but is not what the roadmap asks for.

## 2. Display: two envelopes on primitives mobile already has

`desktop/frontend/src/lib/prefsSync.capacitor.ts` already pulls
`/api/me/preferences` for every key in `SYNCED_KEYS`, including
`profiles_encrypted` and `ssh_hosts_encrypted`. Mobile stores them and does
nothing with them, because it cannot open them.

It turns out the crypto is not the missing piece. `desktop/frontend/src/lib/opaque.ts`
already exports `sealUnsequenced` and `openUnsequencedFrame` — the same
frame-open primitive `sealProfiles`/`sealSSHHosts` route through on the Go
side via `e2eecrypto.SealUnsequenced`. (`deriveSessionKey` itself is
module-private to `opaque.ts`; `openUnsequencedFrame` derives the session key
internally, so a reader never needs to call it directly.) What is missing is
only the envelope around them:

```
value = json string of base64( SealUnsequenced(
            DeriveSessionKey(accountKey, <fixed session UUID>),
            <fixed session UUID>, <AAD tag>, json(payload)) )
```

So each reader is: JSON-decode to a string, base64-decode, `openUnsequencedFrame`
with that key's fixed UUID and AAD tag, `JSON.parse`. Tens of lines, not a
crypto port.

**The risk is cross-language format drift, and it is the main risk in this
item.** A Go-side change to either envelope breaks mobile silently, with
nothing failing in CI — the same shape as the `ssh_hosts_encrypted` bug that
stayed broken for months and the web-dist drift the CI gate was built to stop.

So each reader ships with a **golden vector generated by the Go code**: a Go
test seals a fixed payload with a fixed key, writes the fixture, and the
fixture is committed; a TS test opens it and asserts the decoded contents.
Change the Go envelope and the Go test rewrites the fixture, and the TS test
fails on the next run. The fixture is the contract, and it is generated —
never hand-written, because a hand-written fixture encodes what someone
believed the format was.

Direction is one-way: mobile reads these two keys and never writes them (§6).

### What mobile shows

- **SSH hosts:** alias/host, user, port, tags, note, and whether the host has
  a jump chain or is a `ProxyCommand` host (which nothing will dial). Read-only.
- **Profiles:** name, shell, cwd, startup command, and env **only when
  `SyncEnv` is true** — `stripUnsyncedEnv` clears `Env` before sealing for any
  profile with `SyncEnv: false`, so mobile has nothing to show for those and
  must say "not synced from that machine" rather than "none".

## 3. Use: ask a desktop to open a session

A new request/response frame pair:

```go
TypeSessionCreate  Type = 0x3b // client -> relay -> desktop uplink
TypeSessionCreated Type = 0x3c // desktop uplink -> relay -> requester client
```

Redline #4 forbids changing the payload structure of **existing** frames. These
are new types; nothing existing is touched and no older client needs to know
about them.

**Routing is by host, not by session — and that is the one place this is not a
copy of `TypeFSRequest`.** FS requests ride `sess.SendInbound` and are keyed by
`SessionID`, which a create request does not have yet. But
`AnnouncePayload.HostID` is an uplink-level field, present independently of the
sessions list, so the relay already knows every connected desktop's host id
even when that desktop has zero sessions. The create request carries a
`host_id`; the relay routes it to the uplink that announced it. The response
routes back to the requesting client only, exactly as `TypeFSResponse` does —
per-requester, never broadcast.

Routable at the relay is not the same as nameable on the phone, though: the
relay can address a zero-session desktop by `host_id` because `AnnouncePayload`
gives it one regardless of session count, but the phone's only source for
*enumerating* hosts to offer in the picker is `/api/sessions`, which lists
sessions — a desktop with none does not appear there and so cannot be
selected, even though the relay could route a create request to it if the
phone somehow knew its `host_id`.

**The phone sends a profile ID, never a profile body.** The desktop resolves it
from its own config. That is the security property that makes this safe to
expose: a phone chooses among the desktop's recipes, it cannot write one. A
`startup_cmd` the desktop's configuration does not already contain cannot be
injected. An unknown profile ID is refused, as is a request from a client not
authenticated for that uplink's owner — the same gate `TypeFSRequest` passes.

On success the response carries the new session ID and the phone attaches
through the existing path, as if the session had appeared on its own.

## 4. Bounds

- **One in-flight create per client.** A phone that taps twice does not fork
  two shells. Client identity only exists at the relay (one outbound channel
  per connected client), so this bound lives there — a client with an
  unanswered `TypeSessionCreate` gets refused (`request_in_flight`) until the
  first is answered or reaped after 60s (comfortably above the phone's own
  30s patience, so the relay never reaps a request the phone is still
  waiting on). The desktop separately caps how many creates it will run at
  once (a modest concurrency window, not a per-client count — a desktop
  keeps exactly one uplink connection shared by every client that talks to
  it, so it cannot see per-client identity to bound by), purely as a safety
  valve against an unbounded or buggy/compromised relay.
- There is no per-host session-count cap. An earlier draft of this spec
  proposed one; it was dropped: it counted every session (local tabs
  included) but refused only phone-created ones, so a desktop's own owner
  opening many local tabs would make the phone unusable with an error naming
  a limit the user never set and can't see; it bought no additional
  security, since anything reaching this handler is already authenticated
  for the owner and can already attach, type, and read the filesystem; and
  it was a total-count cap standing in for what is really a rate concern,
  which the phone's no-auto-retry rule and the relay's per-client and
  duplicate-request-id refusals above already cover.
- A create with no response in **30s** fails on the phone and is **not
  retried automatically**. A retried "start a shell" that actually succeeded
  the first time leaves an orphan process the user never asked for.

## 5. Surface

- `Platform.listSSHHosts(): Promise<SSHHostView[]>` — decoded, credential-free
- `Platform.listProfiles(): Promise<ProfileView[]>`
- `Platform.createSessionWithProfile(hostID, profileID): Promise<string>` —
  capacitor only; the wails platform keeps its local `newSession`

The desktop platform does not gain these. It already has profiles and hosts in
process, and routing a local action through the relay would be slower and able
to fail.

## 6. Non-goals

- **No editing from mobile.** Hosts and profiles are read-only on the phone.
  Editing means sealing, sealing means writing a key another device will adopt,
  and a write path from a device that cannot test the result — it cannot open a
  shell to check the profile works — is how you corrupt a config for every
  machine at once.
- **No credential display.** The sealed host blob does contain
  `sshCredential` and `sshKeySecret`. Mobile decodes the records it needs and
  never renders, logs, or copies the secret fields.
- **No SSH from mobile.** Showing the host list is not dialing it. A host row
  is reference material, and later an argument to a desktop-side action.
- **No profile picker for an existing session.** A profile applies at fork
  time; changing one afterwards means re-forking, which is a different feature
  with different consent.
